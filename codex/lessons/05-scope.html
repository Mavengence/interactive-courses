Scoping.
Small Tasks Win.

Codex is great at a morning's work, not a quarter's. Learn the shape of a task it can land cleanly.

⏱ 12 min read ◆ 3 interactives ✦ +50 XP available

There is a size of task that Codex lands cleanly. There is a size of task where it thrashes, produces a sprawling PR, and requires you to untangle three entwined changes on review. The boundary is sharper than you'd think, and once you can see it, you'll start reflexively decomposing work before you hand it over.

The rule of thumb: a task Codex can land in one run is the size of a morning for a mid-level engineer. Roughly:

  • Touches 1–5 files.
  • Involves one concept — not three parallel threads.
  • Has a testable outcome that can be checked in under a minute.
  • Lives entirely inside your existing architecture — no "and also introduce a new service layer."

Bigger than that, quality drops off a cliff. Not linearly — exponentially. A task twice the size is four times as flaky. And because Codex runs are asynchronous, a flaky run costs you the whole round-trip time.

Size the task for the agent, not for the ticket.

Three slicing moves

When a task feels too big, there are three reliable ways to split it. In rough order of ease:

move 01 · horizontal

Split by layer

Big task = schema change + API change + UI change. Three Codex tasks. The schema PR lands, you merge, the API PR builds on it, and so on. Each one reviewable in isolation.

move 02 · vertical

Split by entity

"Add soft-delete" to three entities → three tasks, one per entity. Identical shape, smaller blast radius each. Also: if one of them is tricky, it doesn't block the other two.

move 03 · prep/do

Do the plumbing first

Task 1: refactor the messy part so the next change is obvious. Task 2: make the change. Cleaner than one PR doing both at once — and the prep PR often catches bugs you didn't know about.

The surgical changes principle

There's a discipline that separates effective AI-assisted development from sloppy AI-assisted development: only change what the current task requires. Not what looks messy. Not what you notice along the way. Not the thing three files over that's probably wrong. The task.

This matters more with an AI agent than with a human engineer because the agent has no natural reluctance to touch things. A human gets tired and stops. The agent will cheerfully refactor your entire error-handling layer if the task spec gives it any opening to do so. It means well. But you now have a 600-line PR where 200 lines are the feature and 400 lines are "improvements" you never asked for, never reviewed, and can't easily separate.

The technical term for this is scope creep and it's worse in AI sessions than in human ones because it happens in a single run, invisibly, before you see the output.

cost 01

Review burden multiplies

A 200-line PR takes 20 minutes to review. A 600-line PR — where 400 lines are untasked refactoring — takes 90 minutes. The ratio isn't linear; interleaved changes are harder to reason about than isolated ones.

cost 02

Rollback becomes entangled

If something breaks in production, "revert the PR" reverts everything — the feature, the refactoring, the cleaned-up tests. You can't cleanly separate. A narrowly scoped task is always safe to revert.

The antidote is a single sentence you can add to any task spec: "Only change files directly required for this task. If you notice other issues, note them in the PR description but do not fix them." That one instruction cuts the "bonus work" problem by roughly half.

The other half is fixed by scoping the spec to be so specific that there's no room for interpretation. Compare:

# Too open — invites bonus work
## Goal
Add pagination to the users list endpoint. The current implementation
returns all users; we need page-based results.

# Surgical — leaves no room for wandering
## Goal
Add page and page_size query params to GET /users in api/users.py.
Default: page=1, page_size=20. Max page_size=100 (raise 400 if exceeded).
Return {"items": [...], "total": N, "page": N, "pages": N}.

## Scope
Touch only api/users.py and tests/api/test_users.py. Nothing else.

Recognise the smells

When you catch yourself writing a spec with any of these phrases, stop. Split first.
