Anatomy of a
Task Spec.

Goal, constraints, acceptance criteria, out-of-scope. Four lines, and your success rate roughly doubles.

⏱ 12 min read ◆ 3 interactives ✦ +50 XP available

If AGENTS.md is the agent's onboarding doc, the task spec is the single Jira ticket it works from. It's what gets pasted into the task field when you kick off a run. Everything else — the repo context, the conventions, the tests — is already there. The spec is where you describe the work.

Most people write the spec as a one-line request: "add pagination to the users endpoint." Sometimes that works. Usually it produces a plausible-but-not-quite-right PR that needs two rounds of revision. The problem isn't that Codex is dumb. The problem is that the one-line spec is four specs collapsed together — goal, constraints, acceptance, scope — and the agent gets to pick one interpretation for each.

The core principle: describe the shape, not the steps

The single most important rule in task-spec writing: describe what the end state should look like, not how to get there. Don't instruct the agent step-by-step ("first, open the file, then add a function…"). Instead, describe the outcome: what behavior should exist, what tests should pass, what should not change.

Why? Because the agent is better than you at finding implementation paths inside a codebase it just read. What it cannot do is read your mind. When you describe the shape — "users can page through /users, 20 per page, via ?page=N, keeping the existing response schema" — the agent picks the right implementation. When you describe steps, you're fighting the model's own judgment, and often losing.

Unpack the four parts and the success rate roughly doubles. Here's the anatomy:

The four parts

01 · goal

What outcome are we after?

One sentence. The user-facing, behavioral change you want — not the implementation steps. "Users should be able to paginate through /users, 20 per page." Not "write a pagination function." Describe the shape, not the steps.

02 · constraints

What shape must the solution take?

The non-negotiables. "Don't change the response schema." "Must work with existing query params." "No new dependencies." These close off whole branches of bad design.

03 · acceptance

How will we know it's done?

The checklist the PR must pass. "A new test covers page 1, page 2, and out-of-range. make test passes. No deprecation warnings." Concrete, checkable. Codex will literally run these.

04 · out of scope

What are we explicitly not doing?

The negative space. "Don't touch auth." "Don't refactor the query builder even if it's tempting." Prevents the agent from "helpfully" enlarging the PR and breaking unrelated things.

Anatomy of the strong version

The strong spec isn't longer because the author is fussy. It's longer because it closes the ambiguities that would each, individually, cost you a round of revisions:

  • "20 per page" — Codex won't have to guess the default page size.
  • "?page=N query param" — closes off cursor-based pagination, offset hacks, and response-envelope redesigns.
  • "Keep the existing response schema; add a pagination field" — tells the agent exactly where the new data goes.
  • "make test must pass" — concrete, checkable.
  • "Don't change the filtering logic" — guards against the refactor urge.

The strong spec is roughly 80 words. Writing it takes sixty seconds. The alternative is a PR-review round-trip that costs you twenty minutes.

Notice what the strong version doesn't do: it never says "first open api/users.py, then find the list function, then add an offset parameter." It describes the end state. The agent reads the codebase and finds the right place. That's the whole point of delegating.
