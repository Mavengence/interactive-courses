Reviewing a
Codex PR.

It wrote 400 lines. Three are subtly wrong. Here's the review checklist that catches them — every time.

⏱ 14 min read ◆ 3 interactives ✦ +55 XP available

Reviewing a Codex PR is not the same as reviewing a human PR. The failure modes are different. The biases are different. The things you'd gloss over on a teammate's patch are the exact things worth scrutinizing on an agent's.

Humans make interesting mistakes — typos, off-by-ones, missed edge cases. Codex makes plausible mistakes. Code that looks right, has the right shape, passes the tests it wrote, and is subtly wrong in a way that only shows up at 3am on a Sunday.

The fix is not to trust less. It's to have a specific checklist, run it every time, and stop relying on the "I'll know it when I see it" reflex. Because you won't.

Trust, but diff. Every line. Every time. It takes fifteen minutes and it's worth every one.

The review checklist

Six checks, in order. Each one catches a class of Codex-specific failure. Don't skip. Don't reorder — the early ones save you time on the late ones.

check 01

Does it do what you asked?

Read the PR title and description against your task spec. Codex sometimes solves a nearby problem instead of the one you posed. Catch this first — it's the most expensive failure to miss.

check 02

Is it the right size?

Skim the file list. If it touches more files than you expected, the agent did extra work. Sometimes that's fine; sometimes it's scope creep. Compare to what you'd expect a careful human to touch.

check 03

Do the new tests actually test?

The #1 subtle failure. Tests that mock the thing they're supposed to verify. Tests that assert the code ran (not that it worked). Read every new test and ask: "would this fail if the implementation were broken?"

check 04

Are there new dependencies?

Search the diff for imports you don't recognize, or changes to requirements.txt/package.json. Codex is happy to pull in a new library. You should be less happy.

check 05

What did it delete?

The red lines are where bugs hide. Codex occasionally deletes things it thinks are redundant — a comment that was load-bearing, a test it reads as "outdated," a fallback that's actually the fallback.

check 06

Does it match the house style?

Error handling, logging, naming, test structure. If it feels like someone else's code, that's usually a sign AGENTS.md was thin — and a signal to strengthen it for next time.

The subtly-wrong test — a real example

Here's a real pattern we see all the time. The spec asked for "a rate limiter on /login." The test file looks fine. Find the problem before scrolling.

# tests/api/test_login_rate_limit.py

def test_login_rate_limit_blocks_after_5(client, mocker):
    mock_limiter = mocker.patch("api.auth.limiter.is_allowed")
    mock_limiter.return_value = False

    response = client.post("/login", json={...})

    assert response.status_code == 429
    mock_limiter.assert_called_once()

The test passes. The test proves nothing. It mocks is_allowed to return False, then asserts that /login returns 429 — which is what the mock made happen. The actual rate limiter could be completely broken. The test would still go green.

Compare with the version that actually verifies behavior:

# the one that actually tests something

def test_login_blocks_at_6th_attempt(client):
    for _ in range(5):
        r = client.post("/login", json={...})
        assert r.status_code == 401  # bad creds, allowed

    r = client.post("/login", json={...})
    assert r.status_code == 429  # blocked

The security pass

AI-generated code has a characteristic security failure mode: it solves the stated problem correctly while ignoring the implied security constraint you assumed was obvious. The agent wasn't careless — it just wasn't told. A five-minute targeted pass after the functional review catches the most common class.

sec 01

Input trust boundary

Trace every user-controlled value. Does it flow into a query, a file path, a shell command, or an HTML response without sanitization? Codex frequently omits validation when the spec doesn't mention it.

sec 02

Authentication bypass

New endpoints need auth guards. Codex often adds the endpoint correctly but forgets to apply the decorator, middleware, or policy that gates it. Grep every new route for your auth annotation.

sec 03

Secrets in source

Hardcoded API keys, tokens, or connection strings appear when the agent copies an example from its training context. Grep the diff for anything that looks like a credential before merging.

sec 04

Error message leakage

Agents tend to return raw exception text in API responses — easy to add, looks fine in tests. An except e: return str(e) leaks stack traces, schema details, and sometimes credentials to callers.

▸
Concrete grep pattern: after every Codex PR, run git diff main...HEAD | grep -E "(password|secret|token|api_key)\s*=" and grep -rn "except.*:" --include="*.py" on changed files. Two commands, thirty seconds, catches the two most common AI-specific security misses.

Here's a before/after that shows the pattern. Spec was: "add a /debug/user endpoint." The agent completed the task correctly — but:

# what Codex produced — functional, insecure

@app.route("/debug/user")           # no auth guard
def debug_user():
    user_id = request.args.get("id")  # no validation
    try:
        u = db.session.query(User).get(user_id)
        return jsonify(u.__dict__)       # exposes all columns
    except Exception as e:
        return str(e), 500              # leaks stack trace

# corrected version — same feature, secure

@app.route("/debug/user")
@require_admin                         # auth guard restored
def debug_user():
    user_id = int(request.args.get("id", 0))  # validated
    try:
        u = db.session.query(User).get(user_id)
        if not u: return jsonify({"error": "not found"}), 404
        return jsonify(u.to_safe_dict())  # explicit field allowlist
    except ValueError:
        return jsonify({"error": "invalid id"}), 400  # safe message
