AGENTS.md —
Codex's Memory.

One file, committed to your repo. It's the difference between "write a PR" and "write a PR the way we write PRs here."

⏱ 11 min read ◆ 3 interactives ✦ +55 XP available

Codex has no persistent memory. The sandbox is ephemeral. The agent has never met your team before. Yet, somehow, people get Codex to produce PRs that look like the humans on the team wrote them — same error-handling conventions, same test patterns, same casual profanity in commit messages. How?

Answer: AGENTS.md. A plain-text file, in your repo root, that Codex reads at the start of every task. It's your onboarding doc for the agent. The new-hire manual that the new hire actually reads on day one.

The concept is the same across tools. Claude Code uses CLAUDE.md. GitHub Copilot Workspace uses a repo instructions file. Cursor uses .cursorrules. The names differ; the principle is identical: a plain-text file committed to your repo that the agent reads before it touches anything. This lesson uses AGENTS.md as the canonical example — apply everything here to whatever convention file your tool expects.

Anything worth knowing about how your team builds software belongs here. Conventions. Folder structure. Test commands. Known quirks. The one library you love and the one you're migrating off. The exact set of things a competent junior engineer would pick up by osmosis over their first six weeks — except you're writing it down, once, and every agent run benefits.

Think of AGENTS.md as the onboarding doc you wish your team had written years ago. Now you have a reason to write it.

What a good AGENTS.md contains

There's no schema. The file is read as context. But a few sections pay off reliably across every repo we've seen:

A real one, condensed

Here's the shape of a production AGENTS.md. Not a template — a sample. Your file should look nothing like this structurally. It should look exactly like this in specificity.

# AGENTS.md

## What this repo is
Payments service. Python 3.11, Flask, Postgres, Stripe.
Critical path: /checkout endpoint. Downtime costs money literally.

## Running locally
$ make setup       # installs everything
$ make test         # pytest, must pass before any PR
$ make lint         # ruff + mypy, also mandatory

## Conventions we actually enforce
- No bare except: clauses. Catch specific exceptions.
- Every endpoint gets an integration test in tests/api/.
- Log with structlog, never print. Log context as kwargs, not f-strings.
- Migrations go in db/migrations/, numbered, never edited after merge.
- We use pydantic v2. If you see v1 patterns, flag it — we're mid-migration.

## Known quirks
- tests/integration/test_webhooks.py is flaky. Re-run once before debugging.
- user_service.py has 400 lines we've been meaning to split. Don't make it worse.
- Our Stripe test keys live in .env.test, already in the sandbox.

## Definitely don't
- Touch legacy/ without explicit permission — it runs in prod, unowned.
- Add new top-level dependencies without asking.
- Write code in server_v1.py. It's deprecated.

The before/after

Same task — "add a /health endpoint that checks the database." Same repo. The only variable: whether AGENTS.md was present. Look at the resulting patches.

Quick check

Rolling it out

Three moves to get value out of AGENTS.md in a week:

  1. Start with 30 lines. A half-page is better than a perfect document that never ships. Answer: what does this repo do, how do I run it, what are three things a new hire always gets wrong?
  2. Grow it from rejections. Each time you reject an agent PR for a stylistic reason, add a line to AGENTS.md so the next run doesn't repeat the mistake. The file should get measurably smarter every sprint.
  3. Review it like code. The file is source. When conventions change, AGENTS.md changes. Stale docs poison the well worse than missing docs.

Context management: what goes in, what stays out

The convention file competes for space in the context window with your task spec and the repo contents the agent reads. Keep it focused:

  • In: things that change how code is written (conventions, patterns, must-avoid). Anything a new engineer would ask on their first week.
  • Out: things the agent can infer from the code itself (don't describe your folder structure if it's obvious). Marketing copy, meeting notes, personal preferences.
  • In: exact commands. make test, not "run the tests." The agent executes commands literally.
  • Out: vague principles. "Write clean code" adds no signal. "No bare except: clauses — catch specific exceptions" does.

A 200-line AGENTS.md that is specific and accurate outperforms a 600-line one that's half filler. Prune aggressively. Every line should earn its spot by preventing a real mistake.

▸
Tool-specific note. Claude Code reads CLAUDE.md and supports directory-level convention files (e.g., src/CLAUDE.md for frontend-specific rules). If you're using Claude Code on a monorepo, layer your convention files: root-level for universal rules, directory-level for domain-specific ones.
