The three delivery guarantees

Every messaging or pipeline system promises one of three:

  • At-most-once. Messages may be lost; never duplicated. Cheap. Used for fire-and-forget metrics.
  • At-least-once. Messages are never lost; may be duplicated. The default for almost every distributed system. Cheap to implement; pushes deduplication onto consumers.
  • Exactly-once. Messages are processed exactly once. Sounds great. Almost always means something subtler than you think.

The dirty truth: "exactly-once" is at-least-once delivery + idempotent processing. The system can't actually prevent the message from being delivered twice — it can only ensure that the second delivery has no observable effect. So "exactly-once" really means "the side effects are idempotent." If your sink is a Kafka topic with transactional commits, that idempotency is built in. If your sink is "POST to a credit card processor," exactly-once is your problem to solve.

Idempotency in practice

Three patterns to make any operation idempotent. Memorize them.

01
UPSERT by key
the common one — fact tables, dim updates
MERGE INTO fact_orders dst
USING new_orders src
  ON dst.order_id = src.order_id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...
re-runnable · order-independent
02
Windowed overwrite
daily aggregates, rolling cohorts
BEGIN;
DELETE FROM agg_daily
  WHERE day = '2026-04-15';
INSERT INTO agg_daily
  SELECT … WHERE day = '2026-04-15';
COMMIT;
atomic · safe to retry whole window
03
Dedup by event_id
streaming sinks, at-least-once consumers
INSERT INTO sink (event_id, …)
VALUES (…)
ON CONFLICT (event_id)
  DO NOTHING;
producer must emit stable id

Backfill, the right way

A backfill is the operation of re-running a pipeline over historical input — usually because the original run had a bug, or you need to populate new columns. Backfills are where bad pipelines reveal themselves.

▸
The IC5 backfill checklist. (1) Does my job take an explicit window parameter, not "yesterday"? (2) Will running window N twice produce the same result? (3) Will running windows N and N+1 in parallel produce the same result as serially? (4) Can I run a backfill without breaking the live job? If any answer is no, fix that before you ever push.

How Kafka achieves exactly-once

Kafka's transactional API is the cleanest implementation of streaming exactly-once you'll see. Three pieces:

  1. Idempotent producer. Every producer gets a producer ID (PID) assigned by the broker on first connection. Every record gets a monotonically increasing sequence number per (PID, partition). The broker deduplicates in-memory: if a record with sequence N arrives and N was already accepted, it's silently dropped. This covers producer-level retries.
  2. Transactions across topics. A producer can beginTransaction(), write to multiple topics/partitions, then commitTransaction() or abortTransaction(). Until commit, consumers with isolation.level=read_committed don't see any of the records. Atomicity is enforced by a transaction coordinator (a broker-side component keyed by transactional.id).
  3. Consumer offsets in the transaction. The consumer's offset commit is written to __consumer_offsets inside the same transaction as the output records. So "I read offsets M–N and produced these records" either both commit or both abort. This is what makes a consume-transform-produce pipeline exactly-once for the Kafka-to-Kafka case.

Result: a Kafka-to-Kafka pipeline can guarantee exactly-once end-to-end. As soon as the sink is anything other than another Kafka topic — a Postgres DB, an HTTP API, an S3 file — it's back on you to make the side effect idempotent. Flink's two-phase commit sink extends this: Flink checkpoints write a pre-commit to the external sink (e.g., Iceberg stage files), then the commit is triggered only after the Kafka offset commit succeeds — bridging Kafka's transactional exactly-once to external sinks that support a commit/abort protocol.

kafka exactly-once: scope table
Pipeline Guarantee Mechanism
Kafka → Kafka Exactly-once Transactional API, offset commit in tx
Kafka → Iceberg (via Flink) Effectively exactly-once Flink 2PC sink + checkpoint
Kafka → Postgres At-least-once + idempotent UPSERT on key or ON CONFLICT DO NOTHING
Kafka → HTTP API At-least-once only Idempotency key (client-generated UUID)

Dead-letter queues: the proof of intent

A pipeline that claims exactly-once semantics but silently drops malformed records is lying — it's at-most-once with extra steps. The IC5 move is a dead-letter queue (DLQ): any record that fails processing or schema validation is routed to a dedicated topic or table, not discarded.

A well-designed DLQ captures:

  • The original raw bytes of the failed record (don't rely on deserialization succeeding)
  • The exception type and message
  • The source topic, partition, and offset — so you can replay the record once the bug is fixed
  • A timestamp and consumer group ID for tracing

The DLQ doesn't fix the bug — it makes failures observable and recoverable instead of invisible and permanent. In Kafka, implement this with a try/catch in your consumer loop; in Flink, use getSideOutput() with a tagged OutputTag for poison records. Alert on non-zero DLQ throughput the same way you'd alert on non-zero error rate in a web API.

▸
Interview test. If asked "how do you handle bad records in your pipeline?" — "I drop them with a log line" is a red flag at IC5. The answer is a DLQ with the original bytes, the exception, and the source offset, plus an alert on non-zero DLQ writes and a documented replay procedure. This is the difference between a pipeline that looks correct and one that is demonstrably correct.

Schema evolution: the hidden third axis

A backfill that you didn't anticipate: the schema changed. Six months ago you ingested events with 12 fields. Today's events have 14 — two new fields were added. You want to backfill the new columns into old data.

Three compatibility modes you'll see in schema registries:

  • Backward. New schema can read old data. (Old field deleted? OK, just ignored. New field added? Must have a default.) Lets you upgrade consumers first.
  • Forward. Old schema can read new data. (New field? Old reader ignores. Removed field? Old reader gets a null/default.) Lets you upgrade producers first.
  • Full. Both. The strictest, most flexible setting. Default for new pipelines.

Set the registry to FULL by default. The day a producer ships a breaking change without coordinating, you'll be glad the registry rejected it.
