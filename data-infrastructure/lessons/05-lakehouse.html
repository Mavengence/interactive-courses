The lakehouse:
ACID, finally.

Iceberg, Delta, Hudi. Three table formats that put a transactional metadata layer on top of Parquet files in object storage. Snapshots, time travel, schema evolution — and the format war, ranked.

Learning objectives. After this lesson you can: (1) explain the five-layer Iceberg metadata stack and trace a read and a write through it; (2) describe how optimistic concurrency control delivers ACID semantics on object storage; (3) compare Iceberg, Delta, and Hudi on engine support, update strategy, and sweet spot; (4) distinguish Copy-on-Write from Merge-on-Read and pick the right one for a given workload.

For a decade, the data lake was a directory of Parquet files on S3, and that was it. It was wonderful — cheap, durable, scalable — and it was missing everything: no atomic writes, no schema evolution, no time travel, no concurrent updates without corruption, no idea which files belonged to which version of the table. To delete one user's data for GDPR, you rewrote the entire dataset.

The lakehouse fixes this with one architectural move: add a metadata layer on top of the file layout that tracks which files belong to which version of the table. Three formats compete to be that layer:

  • Apache Iceberg — born at Netflix, donated to Apache, the reference implementation people pick for openness. Engine-agnostic.
  • Delta Lake — born at Databricks, open-sourced under Linux Foundation, deeply integrated with Spark. Now interoperates with Iceberg via UniForm.
  • Apache Hudi — born at Uber, optimized for streaming upserts and CDC. Niche but excellent at its niche.

The metadata layer, in three layers

A read goes top-to-bottom. The catalog tells you the current metadata file. The metadata file points to the current snapshot's manifest list. The manifest list lets you skip whole manifests via partition stats. Each surviving manifest tells you which data files to actually read — and you can prune those further via per-file column stats. Then you read just those Parquet files.

A write is the reverse. You write new data files. You write a new manifest pointing to them. You write a new manifest list. You write a new metadata file. Then — and this is the key — you do a single atomic compare-and-swap on the catalog pointer, from v17.json to v18.json. That's the commit. Either it succeeds and the new snapshot is live; or it fails and your draft files are orphaned (and cleaned up by VACUUM later).

ACID on object storage: optimistic concurrency control

Object storage has no lock server. How can two concurrent writers avoid corrupting the table? The answer is optimistic concurrency control (OCC): both writers proceed in parallel, and only the last step — swapping the catalog pointer — is serialized.

  1. Writer A and Writer B both read the current metadata pointer: v18.json.
  2. Both write their new data, manifests, and metadata files in isolation.
  3. Writer A commits first: the catalog atomically swaps from v18.json → v19a.json. Succeeds.
  4. Writer B tries to swap v18.json → v19b.json. The CAS fails — v18.json is no longer current. Writer B either retries (reading the new base) or raises a conflict error.

This gives you serializable isolation for non-conflicting writes at essentially zero cost. Most concurrent writers don't touch the same rows; OCC lets them all proceed and only serializes the metadata pointer swap. Row-level conflict detection (e.g. two writers updating the same row) is format-specific — Delta uses transaction logs with conflict predicates; Iceberg uses manifest-level conflict detection.

Catalogs and the REST standard. The catalog is whatever service holds the table name → current metadata file mapping. Common options:

  • Hive Metastore (HMS) — the classic, a relational DB (usually MySQL) fronted by a Thrift service. Works everywhere; operationally heavy.
  • AWS Glue Data Catalog — managed HMS-compatible service in AWS. Zero-ops for AWS shops.
  • Project Nessie / REST catalog — git-for-data semantics (branches, tags, merges). Nessie is the reference implementation; the Iceberg REST catalog spec lets any HTTP server act as a catalog.
  • Unity Catalog (Databricks) — governance-first, fine-grained access control, multi-cloud. The catalog of choice in the Databricks ecosystem.

CoW vs MoR — the real format war

The deepest architectural decision in any lakehouse is how it handles updates and deletes. Object storage doesn't support in-place edits. So when you say UPDATE orders SET status='shipped' WHERE id=42, the engine has two strategies:

  • Copy-on-Write (CoW). Find the data file containing row 42. Rewrite it without that row. Add a new file with the updated row. Atomically swap. Fast reads (each row exists in exactly one file), slow writes (rewrites whole files for one-row changes), write amplification.
  • Merge-on-Read (MoR). Don't touch the data file. Write a small "delete marker" file recording "row 42 in file abc.parquet is dead". At read time, the engine reads the data file and the delete files, merges them on the fly, returns the merged result. Fast writes, slower reads, compaction needed to keep read latency reasonable.

Iceberg supports both, picks per-table. Delta is CoW by default with deletion vectors as an MoR-flavored optimization. Hudi pioneered MoR and it's their default. Rule of thumb: infrequent updates + read-heavy → CoW; frequent CDC-style updates → MoR.

The 2026 reality. Iceberg has won the multi-engine open standard. Snowflake, BigQuery, Athena, Databricks all read it natively. Pick Iceberg unless you have a specific reason — and "I'm a heavy Databricks shop" is one of the few good ones.

Quick check

Key takeaways

  • The metadata layer is the product. Iceberg/Delta/Hudi are not storage systems — they are metadata management layers on top of Parquet on object storage. ACID comes from atomic CAS on the catalog pointer, not from the storage layer itself.
  • OCC, not locking. Concurrent writers use optimistic concurrency control: both write in parallel; only the final catalog pointer swap is serialized. Conflict = retry, not deadlock.
  • CoW vs MoR is a read/write trade-off. Read-heavy, infrequent updates → CoW. CDC-style high-frequency upserts → MoR. Most formats support both; choose per table.
  • Iceberg hidden partitioning removes a class of bugs. Hive-style partitions require writers to maintain a separate physical column; hidden partitioning (Iceberg) derives it from the source column, so changing the partition granularity is a metadata-only migration.
  • Pick Iceberg for multi-engine. If queries come from more than one engine (e.g. Spark writes, Trino reads, Athena ad-hoc), Iceberg's engine-agnostic spec is the safest long-term bet.
