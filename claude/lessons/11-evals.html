Prompt Debugging
& Evals.

Vibes are not a measurement. How to know a prompt is actually better.

⏱ 12 min◆ 4 interactives✦ +85 XP

You tweak a prompt. The next response "feels better." Is it? You don't know. That's the problem.

Anthropic's prompt engineers say it plainly: approach prompting like a scientist — test and iterate. Evals are the test suite. They don't need to be fancy; they need to exist. Five realistic examples beat a thousand gut checks.

No eval, no improvement — just drift.

The minimum viable eval

You don't need a platform. You need five examples.

eval_v1:
  - input:    <realistic example 1>
    expects:  <what a good output looks like>
  - input:    <realistic example 2, including a hard edge case>
    expects:  <…>
  - input:    <example 3, a known failure mode>
    expects:  <…>
  - input:    <example 4>
    expects:  <…>
  - input:    <example 5, adversarial — empty input, ambiguous input>
    expects:  <…>

Before you change the prompt, run all five. Save the outputs. After you change the prompt, run all five again. Diff.

Debugging a broken prompt

When a prompt misbehaves, resist the urge to add instructions. First, remove. Prompts rot when people pile on. Start with the minimum that should work. If it works, reintroduce constraints one at a time until it breaks. That's your culprit.

★
Binary search your prompt. Delete half. Works? The problem was in the deleted half. Doesn't work? The problem's in the kept half. Repeat.

Judging quality with a second model

For harder-to-grade outputs ("is this a good review?"), use Claude itself as a judge. Give it a clear rubric, the output to judge, and ask for a score + justification. It's noisy but cheap, and it scales.
