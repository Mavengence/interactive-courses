The CLAUDE.md
File.

Write it once. Never re-explain your stack, your conventions, or your anti-patterns again. This is how Anthropic's own engineers work.

⏱ 9 min◆ 4 interactives✦ +85 XP

A CLAUDE.md is a plain markdown file at the root of your project. Claude Code reads it automatically at the start of every session and injects it into context before it sees your first message. Think of it as a standing brief — the stuff you'd otherwise retype into every prompt.

Anthropic's own engineering team treats CLAUDE.md as the single most impactful lever for improving Claude's output in a repo. The reason is simple: if Claude is a brilliant new hire, CLAUDE.md is the onboarding doc they re-read every morning.

Stop teaching Claude your project once per conversation. Teach it once, in a file, forever.

How the hierarchy actually loads

CLAUDE.md files cascade. Understanding the cascade saves you hours of confusion.

# Loaded into every session, in this order:
~/.claude/CLAUDE.md              # Your global preferences
<repo>/CLAUDE.md                 # Team-shared project rules (commit this)
<repo>/CLAUDE.local.md            # Your personal overrides (gitignore this)

# Loaded lazily, only when Claude touches files in that folder:
<repo>/frontend/CLAUDE.md
<repo>/services/auth/CLAUDE.md

Rules combine, they don't replace. All levels apply at once; more-specific levels win on conflicts. Descendant CLAUDE.md files are lazy-loaded — Claude only pulls them into context when it actually reads files in that directory. This is a big deal in monorepos: you can document each service's conventions next to its code without paying the token cost on every session.

What goes in it

Keep in

  • What the project is, in one sentence
  • Stack, tooling, notable libs
  • Coding conventions the team enforces
  • Commands (build, test, lint)
  • Things never to do (anti-patterns)
  • Where the important docs live (docs/architecture.md, etc.)
  • Terminology that has project-specific meaning

Leave out

  • Secrets, tokens, keys — ever
  • Full files — link or reference with @path/to/file.md
  • Historical context nobody needs
  • Vibes ("write good code"). Be specific or delete.
  • Ad-hoc knowledge that belongs in docs/ and gets pulled in on demand
★
The size rule. Every byte of CLAUDE.md burns tokens on every session. Keep it lean. If something is only needed sometimes, put it in docs/ and reference it (@docs/architecture.md) when relevant.

A battle-tested template

# <Project name>

## What this is
One or two sentences. Who uses it, what it does. Link to the README for more.

## Stack
- Language / framework / versions
- Build + test tools
- Notable libs Claude should know about

## Conventions
- File layout rules (e.g. "colocate tests as `*.test.ts`")
- Style rules the team enforces
- Naming conventions
- Error-handling pattern

## Commands
- `yarn build` — production build
- `yarn test` — unit tests (run before committing)
- `yarn test:e2e` — e2e suite (slow, only on CI)
- `arc lint` — linter + formatter

## Don't
- Add new npm deps without asking
- Use `any` in TypeScript
- Edit files in `generated/`
- Ship code without a matching test

## Terminology
- "Workspace" (not "project") — our product uses this term consistently
- "Member" (not "user") in customer-facing copy

## Where things live
- Source: `src/`
- Tests: colocated (`*.test.ts`)
- Architecture notes: `@docs/architecture.md`
- Deployment: `@docs/deploy.md`

Auto memory: the new half of the system

Recent Claude Code versions add auto memory — Claude writes its own notes to a separate memory file as it learns your preferences, without you typing anything. Correct it once ("we prefix debug logs with [DEBUG]"), and it'll remember next session.

Two things carry knowledge across sessions now:

  • CLAUDE.md — instructions you write, to steer behavior deliberately.
  • Auto memory — notes Claude writes, accumulating from your corrections.

Use CLAUDE.md for things you want a team to share and version-control. Let auto memory pick up personal habits. Don't try to hand-maintain both.
